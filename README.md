# GenchiGenpo
日々の通勤や業務中の歩数を「現地現物へのパトロール（巡回）」に見立て、みんなで歩数を競いながら様々な目的地（宿場町、海外工場、テストコースなど）を目指す
和風・現場主義ウォーキングアプリ

複数人のチームで歩数を共有・管理するウォーキングアプリの要件定義と技術選定のまとめ。

---

## 1. システム要件 & 機能概要
- **コア機能:** 複数人のチームでメンバーの歩数を記録・管理・共有する。
- **不正アクセス対策:** 
  - 無料枠内での運用を絶対条件とし、予期せぬ大量アクセスによる「パケ死（高額課金）」を防止する。
  - バックエンドの手前で認証を必須とし、不正なBotやスクリプトによるデータ読み書きを遮断する。

---

## 2. 技術スタック（選定候補とトレンド）

### 📱 フロントエンド
当初はWebアプリ（React）を検討。歩数取得の端末制限（特にiOS）を考慮し、要件に合わせて以下のいずれかを選択する。
- **候補：Next.js（Webアプリ / PWA化）**
  - **理由:** Reactベースの最新トレンド。ただし、iPhone（iOS）の歩数データをブラウザから直接取得できない制限があるため、Google Fitなどの外部クラウドAPI連携、またはスマートウォッチ（Fitbit等）のAPI連携が必要。

### ⚙️ バックエンド（無料サービス）
個人開発・小規模チーム向けに、無料枠（Free Tier）が充実している以下のBaaS/サービスを採用する。

- **Supabase (オープンソースのFirebase対抗馬)**
  - **選定理由:** PostgreSQL（関係性データベース）が無料で使えるため、「ユーザー」「チーム」「歩数履歴」のリレーショナルなデータ構造を綺麗に設計できる。
  - **安全面:** 無料プランのままであれば自動で有料に移行しない。標準でAPIのレートリミット（回数制限）機能がある。

---

## 3. データベース設計イメージ（Firebase/Firestore想定）
正式な設計はDDDで別途おこなうため、こちらは参考とする。
- **`users` コレクション (ユーザー情報)**
  - `uid` (ユーザーID)
  - `display_name` (表示名)
  - `team_id` (所属チームID)
- **`teams` コレクション (チーム情報)**
  - `team_id` (チームID)
  - `team_name` (チーム名)
- **`steps` コレクション (歩数データ記録)**
  - `doc_id` (一意のID。例: `ユーザーID_日付`)
  - `uid` (ユーザーID)
  - `date` (日付: YYYY-MM-DD)
  - `step_count` (歩数)
